# 30｜Agent 评测：回放、任务成功率与发布回归

> 源码基线为 DeepSeek Harness `dsh-v0.2.3-alpha.2`，提交 `4b399c39a6d1479cd84ca591b4d7c88e24d38a96`。[系列目录](../README.md) · [上一篇](29-observability-token-cost-and-performance.md) · [上游仓库](https://github.com/deepseek-ai/deepseek-harness)

给 Coding Agent 换一版 Harness。它会更早调用搜索工具，也会在生成补丁后多检查一次。快照全通过，任务成功率增加 3 个百分点，平均成本却上涨 40%。这些证据回答的是三个不同的问题：已知路径是否仍可用、模型是否更常完成任务、用户是否愿意为这些收益付出额外成本。发布判断应把三者关联到同一批任务。

## 1. DSH 的测试分层各自能证明什么

| 层级 | 用到什么 | 适合拦住什么回归 |
| --- | --- | --- |
| Unit | 对解析器、投影、注册表或状态机做具体断言。 | 边界错误、非法状态、事件顺序和竞态。 |
| 契约与真实组合 | 保留真实 Loader、服务和工具执行链，可脚本化模型、时钟与外部接口。 | 插件装载、跨组件协议、取消、资源释放以及构建后入口错误。 |
| Session Snapshot | 用已录制的模型输出启动所选 profile，比较规范化后的日志、请求与宿主副作用。 | 固定模型行为下的 Harness 回归。 |
| Web Snapshot | 在浏览器加载构建后的 Web 产物，比较会话驱动的界面输出与纯 UI 预期。 | 渲染、交互与可访问性回归。 |
| 真实 API E2E | 通过真实 Provider 驱动 Agent，用进程和文件等外部事实验收。 | 接口、模型、路由与执行环境实际组合时才出现的问题。 |

DSH 把很多契约用例放在包的常规测试里，也有从真实入口启动的测试。历史 ACP 复盘里，手动挂载的测试覆盖了桥接行为，但真正从 Loader 加载时，导出形态让必需依赖没按预期注入。测试需要证明发布产物会经过同一条关键路径。覆盖率可以帮忙找未执行代码，功能保证还要靠对状态和结果的断言。[仓库分层](../deepseek-harness/docs/testing.zh.md#层级) · [真实入口约定](../deepseek-harness/docs/testing.zh.md#测试真实入口路径) · [ACP 装载复盘](../deepseek-harness/docs/postmortem/0001-acp-default-export-drops-inject.zh.md)

真实 API 套件与常规无密钥测试分开配置。没有对应凭据的用例可以跳过，专门的带密钥工作流则显式检查所需凭据是否存在。因此，报告绿色时也要核对实际运行了哪些用例。真实 API 配置允许失败后重试，适合用于兼容性和冒烟。要拿它衡量模型成功率，则需记录首次结果、重试结果与消耗，保持两边执行策略一致。[真实 API 配置](../deepseek-harness/vitest.e2e.config.ts) · [带密钥工作流](../deepseek-harness/.github/workflows/e2e.yml#L111)

## 2. Snapshot 怎样回放模型，同时运行真实 Harness

场景的 `snapshot.yml` 选择 profile、组合、请求头类别及工作区约定。每个 parent 或 child 角色选数值最高的可用规范 fixture，文件名与日志格式版本一致。回放模式把用户输入注入真实 profile 启动的子进程。`llm-replay` 从 Assistant 结算事件展开内嵌流，按记录顺序供给模型调用。缺 `finish` 的异常流需要显式 sidecar 表达。回放组件能在相应消费路径检查录制脚本是否完整消费，以暴露调用次数变化。[Session Snapshot 格式](../deepseek-harness/packages/test-support/session-snapshot/README.zh.md#use-this-package) · [回放脚本提取](../deepseek-harness/packages/test-support/llm-replay/src/index.ts#L457) · [消费校验](../deepseek-harness/packages/test-support/llm-replay/src/index.ts#L1088)

实际运行输出会规范化临时路径、会话身份与时钟等不稳定字段。系统提示词与工具 schema 的稳定预期由对应请求头类别的 pin 保存。之后比较本次持久日志和预期。`apply-patch-update` 就是一条完整路径。fixture 里已有两个源文件。回放提供模型发出的工具调用，真实补丁工具执行修改。预期日志记录两个修改和一个新增。测试还比较完整 `workspace.expected/`，所以只输出「补丁成功」不足以通过。[规范化规则](../deepseek-harness/packages/test-support/session-snapshot/README.zh.md#use-this-package) · [补丁场景清单](../deepseek-harness/snapshots/session/apply-patch-update/snapshot.yml) · [补丁结果](../deepseek-harness/snapshots/session/apply-patch-update/session.v4.jsonl#L24) · [工作区预期](../deepseek-harness/snapshots/session/apply-patch-update/workspace.expected/) · [真实比较](../deepseek-harness/snapshots/session/headless.snapshot.ts#L1693)

`replay` 是默认无密钥路径，以现有录制比较当前输出。`record` 调用真实模型，刷新录制或对应预期。`refresh` 保留回放输入，用它更新允许刷新的基准。评审时应区分可预期的协议变更、暂态噪声和真正的业务副作用。默认不要为了让回放通过而整体接受差异。改变系统提示词后，即使回放仍能完成，真实模型也可能改走另一条路径，这需要在线任务覆盖。[三种模式](../deepseek-harness/vitest.snapshot.config.ts#L33) · [录制与刷新约定](../deepseek-harness/packages/test-support/session-snapshot/README.zh.md#use-this-package)

## 3. 怎样定义任务成功、误调用和人工介入

代码任务的验收端要有独立判据。DSH 的一个真实模型用例先确认原来的 `add.js` 会让测试失败，模型修改后，由测试宿主重新跑 `add.test.js`，同时检查测试文件没被改。另一个 Headless 冒烟从实际 Loader 路径启动，并读取最终文件。前者凸显独立验收，后者覆盖部署入口。在任务集上也可沿用 SWE-bench 的思路，根据预先确定的代码修改条件验证结果。[代码用例的前置验证](../deepseek-harness/apps/cli/tests/profiles/headless/tests/coding-task.e2e.ts#L48) · [外部验收](../deepseek-harness/apps/cli/tests/profiles/headless/tests/coding-task.e2e.ts#L70) · [真实入口冒烟](../deepseek-harness/apps/cli/tests/profiles/headless/tests/real-model.e2e.ts) · [SWE-bench 原论文](https://arxiv.org/abs/2310.06770)

| 指标 | 可执行的定义 |
| --- | --- |
| 任务成功率 | 初始任务中满足全部验收条件的比例。代码任务可以同时要求新用例通过、原有回归通过、受保护文件保持一致。 |
| 工具误调用率 | 先由任务约定定义「选错能力、目标或操作」。记录发生过至少一次误调用的任务占比，并保留按调用次数的辅助口径。 |
| 人工介入率 | 需要用户补充、批准、纠正或接管的任务占比。再按原因分组，当任务本来要求审批时，询问是执行约定的一部分。 |
| 成本和延迟 | 报告每次投放成本、每个成功任务成本和端到端 P95。用于发布的口径应计入失败、重试与超时消耗。 |
| 关键违规 | 以越权操作、未经批准的外部写入或错误接收方等为单独门槛。记录尝试被拒绝、实际执行和结果未知三种事实。 |

模型可以提供结论和解释，评测端用文件、数据库状态、协议回执或独立测试判定结果。语义质量需要评审时，可固定 rubric，抽样做交叉复核，并区分自动判断与人审。评测任务中写清时间上限、允许的工具、身份及完成条件。用户回答需要参与时，要保存可重复的回答策略和是否实际发生接管。

## 4. 配对比较怎样处理波动和失败归因

给每个任务固定仓库提交、初始文件、模型路由、权限、工具版本和预算，然后让基线与候选各自在等价环境中完成同一任务。多次运行按任务组织，并尽可能交错 A/B 顺序，减少同一时段的 Provider 或机器负载倾斜。若要归因到 Harness，只改变本次评审的 Harness 配置。一次运行的成功概率和允许挑选多次尝试中最好一次的成功率，应分别报告。

单次二元配对先看基线和候选分别独有的成功数。只有在任务对可以视为独立时，才用 McNemar 检验判断一边失败另一边成功的比例是否对称。若每个任务多次运行，先对每个任务汇总差值，再以任务为重采样单位估计置信区间。同仓库任务或同一用户场景明显相关时，考虑在更高的组级别重采样。这样能保留配对关系，也能避免把同一场景的多次运行都当作独立证据。[NIST 配对二元检验](https://www.itl.nist.gov/div898/software/dataplot/refman1/auxillar/mcnemar.htm)

失败要区分任务失败和评测无效。Agent 写错、真实用例失败、达到约定上限应保留在结果中。构建机断网、输入 fixture 损坏等评测基础设施故障可标记无效，按统一规则补跑同一任务对，并报告计划数、有效数、缺失数、原因和消耗。如果缺失集中在候选版，直接删掉这些任务会使成功率偏高。发布时要看缺失覆盖及保守口径下的判断。Provider 限流属于哪一类取决于比较目标，用户实际会受影响时，线上可用性指标仍要计入。

## 5. 成功率升 3 个百分点，成本涨 40%，怎么做发布判断

下面是假设数据，用于理解指标。1,000 个配对任务中，两版都通过 670 个，只有基线通过 50 个，只有候选通过 80 个，两版都失败 200 个。成功率从 72% 到 75%，差值为 3 个百分点。80 个改善和 50 个回归应分别检查，尤其要确认回归是否集中于关键任务。平均每次投放成本从 1 到 1.4 个单位。按所有任务的总成本除以通过数，成功任务的平均成本从约 1.39 到 1.87。净多完成 30 个任务，总成本增加 400 个单位，相当于每多完成一个约多付 13.33 个单位。

是否上线还要看置信区间、关键子集和用户价值。即使整体提升有证据，关键场景的回归、预算耗尽或人工接管增加仍可能让候选无法通过门槛。可以预先规定最小有效提升、允许的成本与延迟变化、须通过的关键场景，满足后才分批放量。如果收益集中在少数任务类型，也可以只给该类路由使用候选策略。观察期要保持能检测失败和副作用的回滚条件。

失败样本回归应针对出错的边界。模型输出已经正确但工具把参数路由错，留一条确定性的契约或回放用例。真实 Provider 下持续选错工具，可把任务保留在独立回归集，并记录允许的技能、权限和判定依据。只更新成功路径的快照会漏掉这些问题。发布记录保留模型路由、Harness 版本、任务集版本、结果摘要及未通过的门槛。

## 6. 面试官怎么逐层追问

### 单元测试和 Snapshot 都通过，为什么还要跑真实 API？

从 DSH 解释回放在模型边界提供已知输出，下游仍能执行真实工具和持久化。继续追问换一个提示词后模型是否还会选同样的工具，这要用真实模型路径来判断。再问真实 API 冒烟能否支撑上线成功率，回答应包含任务覆盖与样本分布。

### 怎样防止 Agent 报告「成功」却没完成任务？

代码任务由独立验收重新运行测试，再检查不可修改的文件和真实 diff。继续追问人工评审部分如何控制偏差，回答应能说明固定 rubric、隐藏版本标签以及如何处理意见冲突。

### 两个版本的成功率差 3 个百分点，能直接下结论吗？

先找同任务两版异向通过的计数，再问是否固定了模型、环境和预算。继续追问多次运行与缺失配对，回答应保留任务级比较，补跑时统一规则，同时报告覆盖与不确定性。

### 成本上涨 40%，怎样确定收益值不值得？

先把每次成本、每个成功任务成本和新增成功的边际成本算清楚。再按任务价值、关键回归和人工介入分组。若收益集中在高价值场景，可以设计路由级上线，保持明确的门槛和回滚信号。
